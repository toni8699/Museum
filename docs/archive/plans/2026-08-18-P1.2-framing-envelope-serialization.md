# P1.2 — Framing envelope serialization and route threading

**Status:** shipped 2026-08-18
**Parent:** [P1 camera overhaul](../../plans/2026-08-18-P1-camera-overhaul.md) §B / §D
**Depends on:** P1.1 shell shipped; no engine dependency
**Unblocks:** P1.3 sampler, P1.4 invariants/policy tests, P1.6 authoring UX

## Outcome

Scene JSON can store one optional framing envelope per connection direction.
Validation rejects malformed or unordered bounds. The envelope survives canonical
serialization, project validation, room resolution, route construction, and both
editor-preview clone paths. P1.3 can consume it without another schema change.

Existing projects remain byte-stable. Missing envelope keeps legacy meaning:
full-authored framing (`w = 1`) when directional keys exist. No migration or
default envelope is written during parse, resolve, clone, or export.

Out of scope:

- envelope weighting or `smootherstep` sampling;
- auto-managed/manual policy and first-key defaults;
- envelope handles, presets, history commands, or other UI;
- endpoint overrides, custom curves, or persisted generated endpoints;
- shell, Camera Plan, `/museum`, and `/museum/editor` changes.

## Schema decision

Preserve current directional keyframe arrays. Add one optional direction map to
`SceneConnectionViewTracks`:

```ts
export type CameraFramingEnvelope = {
  enterStart: number;
  enterEnd: number;
  exitStart: number;
  exitEnd: number;
};

export type SceneConnectionViewTracks = {
  forward: SceneCameraViewKeyframe[];
  reverse: SceneCameraViewKeyframe[];
  framingEnvelope?: Partial<
    Record<CameraConnectionDirection, CameraFramingEnvelope>
  >;
};
```

Canonical JSON example:

```json
{
  "viewTracks": {
    "forward": [],
    "reverse": [],
    "framingEnvelope": {
      "forward": {
        "enterStart": 0.1,
        "enterEnd": 0.25,
        "exitStart": 0.8,
        "exitEnd": 1
      }
    }
  }
}
```

Reasons:

- keeps existing `forward` / `reverse` arrays and their consumers stable;
- gives each direction independent bounds;
- permits only one authored direction without synthetic reverse data;
- preserves old JSON bytes when `framingEnvelope` is absent;
- keeps absent direction distinct from an explicitly authored degenerate envelope.

Runtime uses same value shape under a runtime-named alias/type. All boundaries
deep-clone envelope objects; no editor/runtime object aliasing.

## Invariants and validation

Each present envelope must contain exactly four finite numbers satisfying:

```text
0 ≤ enterStart ≤ enterEnd ≤ exitStart ≤ exitEnd ≤ 1
```

Equal adjacent values are valid, including fully degenerate ramps. Reject:

- non-object envelope containers or direction values;
- unknown container, direction, or envelope keys;
- missing required bound fields on a present direction;
- non-number, `NaN`, or infinite bounds;
- bounds outside `[0, 1]`;
- any ordering inversion.

Use stable issue paths such as
`$.connections[0].viewTracks.framingEnvelope.forward.enterEnd`. Add a dedicated
issue code for ordering/range failure (for example
`invalid_framing_envelope`) rather than reusing keyframe progress codes.

Validation runs at both required gates:

1. `parse-document.ts` validates shape, finite/range values, ordering, and
   unknown keys during scene import.
2. `project-layout-semantics.ts` repeats semantic ordering/range checks at the
   project export gate, matching existing defense-in-depth for camera poses.

The project gate must not depend on room geometry for envelope checks.

## Source changes

### 1. Scene and runtime types

- `apps/museum/src/lib/content/scene.ts`
  - add `CameraFramingEnvelope` and optional directional envelope map;
  - export through existing `$lib/content/scene` surface;
  - in `resolveSceneDocument`, copy present forward/reverse envelopes into the
    resolved connection without creating absent values.
- `apps/museum/src/lib/types/museum.ts`
  - add runtime envelope type/map;
  - extend `RuntimeConnectionViewTracks` while preserving directional arrays.

No field belongs on `SceneCameraViewKeyframe`; envelope scopes whole direction.

### 2. Scene codec

- `scene-codec/parse-document.ts`
  - allow `framingEnvelope` beside `forward` and `reverse`;
  - add focused parser helpers for container, direction, and ordered bounds;
  - omit field from parsed document when absent;
  - avoid implicit `{ forward: ..., reverse: ... }` defaults.
- `scene-codec/canonical.ts`
  - deep-clone bounds in fixed field order;
  - emit `framingEnvelope` after directional arrays only when at least one
    direction exists;
  - preserve absent-field byte output exactly.
- `scene-codec/index.ts`
  - keep public function surface unchanged; export new type only if consumers
    cannot obtain it from `$lib/content/scene` without crossing codec boundary.

### 3. Project export semantics

- `apps/museum/src/lib/project/project-layout-semantics.ts`
  - validate each present directional envelope with project-prefixed issue paths;
  - keep room-reference and target-distance behavior unchanged.

### 4. Route threading

- `apps/museum/src/lib/museum/navigation/camera-route.ts`
  - `buildOrientedViewTrack` selects envelope matching oriented direction;
  - copy it onto `CameraRouteViewTrack`; never reverse/remap its progress values,
    because reverse direction owns its own travel-relative envelope.
- `apps/museum/src/lib/museum/navigation/camera-motion.ts`
  - extend `CameraRouteViewTrack` and prepared runtime types with optional
    envelope;
  - carry the value through preparation only; do not change sampling in P1.2.

P1.2 must leave playback identical. P1.3 alone interprets envelope weights.

### 5. Editor clone and keyframe consumers

- `apps/museum/src/lib/editor/helpers/route-clone.ts`
  - deep-clone optional route-track envelope.
- `apps/museum/src/lib/editor/store/camera-preview-controller.svelte.ts`
  - update controller-local clone identically; do not fold the duplicate-helper
    refactor into this increment.
- Audit keyframe mutation/read paths, especially
  `view-keyframe-controller.svelte.ts`, `NodeConnectionsPanel.svelte`,
  `DirectionalKeyframeList.svelte`, timeline dots/controller, selection helpers,
  layout preview state, and reverse-track sync.
  - key counts and iteration continue using directional arrays;
  - deleting last key must not delete `viewTracks` while an envelope remains;
  - reverse-key sync must not copy/overwrite directional envelopes;
  - no key edit silently drops the envelope map.

No new Svelte props, runes, stores, dependencies, or mounted components.
Selection and mount/unmount semantics remain unchanged.

### 6. Docs wording

- Keep FOV language exact: larger FOV = wider / zoomed out; smaller FOV =
  tighter / zoomed in.
- Audit active P1 and camera-tour/persistence contract wording. Fix contradictory
  spec copy only. UI labels/copy wait for P1.6.
- Update `docs/components/camera-tour.md` and `docs/components/persistence.md`
  when implementation lands, because schema/runtime contracts change.

## Implementation order

1. Add shared scene/runtime types and validation helper contract.
2. Parse and canonicalize optional envelope; lock legacy byte stability.
3. Add project semantic validation.
4. Thread through `resolveSceneDocument`, route construction, and prepared motion
   types without sampling it.
5. Patch both route clone paths and audit keyframe consumers for field survival.
6. Add focused tests, run full gates, then update component docs and handoff.

Keep steps independently testable. If route threading exposes broad sampler
changes, stop after codec/runtime propagation; defer interpretation to P1.3.
