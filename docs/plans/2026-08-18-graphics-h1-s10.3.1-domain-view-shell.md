## 1. Ratification record — decision 1: shell inversion (domain×view matrix)

**Status: recorded for ratification.** The sectioning plan scheduled the
shell-inversion ratification (its decision 1, §6) for the S10.1 closeout. The
closeout shipped B0 + Aim but did **not** record the ratification — nothing in
the repo currently authorizes superseding the S10.1 invariants. This plan
records the ratification at the start of S10.3.1, which is its first gate:
**accepting this plan ratifies decision 1.** If it is rejected, B1 stops here
and the B-track is re-sequenced (the matrix would be re-litigated per the
workspace-design doc §5.4 alternatives).

**Ratified decision.** The editor shell becomes a **domain×view matrix**:
`Scene | Camera` is the primary domain switcher (always visible), and each
domain owns a `Plan | 3D` view pair in **fixed `[Plan | 3D]` order everywhere**
(workspace-design §5.1). This formally supersedes the S10.1 shell shape as
follows:

| S10.1 invariant (superseded text) | Successor rule (this shell) |
|---|---|
| **Invariant 1** — persistent dual-switcher shell: primary `[Plan \| 3D]` always visible, secondary `[Scene \| Camera]` mounts only when `viewMode === '3d'` | **Domain×view matrix.** Domain switcher `[Scene \| Camera]` is primary and always visible; view switcher `[Plan \| 3D]` is per-domain and always visible. Scene and Camera are peer domains, not 3D sub-contexts. Two distinct segmented controls, never one 4-tab bar (§3, invariant 1) |
| **Invariant 3** — timeline bottom frame mounts strictly when `viewMode === '3d' && active3dContext === 'camera'` | **Camera-domain timeline.** `EditorCameraTimelineFrame` mounts for the **Camera domain in both views** (persistence rules, §3 invariant 6). The Scene domain never mounts it |
| **Invariant 2 (parts)** — context-specific viewport toolbars / View menus, no duplication | **Toolbar ownership reconciled.** 3D cells keep the viewport toolbar (Scene `Select | Move | Rotate | Scale | Local/World | Snap | View`; Camera `Select | Move | Rotate | Add camera | View`). The Camera domain gains a **left context tool rail** slot; an action may live in exactly **one** location per cell (§3 invariant 5). Plan cells own 2D toolbars |
| **Invariant 4 — relic isolation** | **Preserved unchanged.** `/museum/editor` stays frozen; every shared-component change stays guarded via the H1 context props |

**Preserved S10.1 guarantees (not superseded):** no new store or document
(`EditorViewState` remains the pure state holder); context memory; Plan
mutation-safety (strengthened: only the Scene → Plan cell authors layout);
relic isolation; one history entry per authored mutation; the
`layout > scene > camera` selection priority is replaced by **domain-gated**
selection resolution (§4) — a deliberate, scoped change to
`deriveActiveSelection`, not to the selection slots themselves.

**Boot default (deferred, non-architectural):** the workspace-design §7 Q4
preference for `Scene → 3D` is **not** part of this slice. Boot stays
`Scene → Plan` (today's behavior); the domain axis defaults to `scene`, the
scene view to `plan`, the camera view to `3d`. Changeable later with no
architecture impact.

## 2. Goal

Replace the 3D-only `Scene | Camera` sub-context with two peer domains, each
owning a `Plan | 3D` view pair, so the Camera domain can host a 2D graph
surface (S10.3.2) and the camera timeline persists across both views:

```text
[Scene | Camera]                     ← domain switcher (primary, always visible)
  Scene → [Plan | 3D]                ← layout authoring        | scene authoring
  Camera → [Plan | 3D]               ← camera graph (S10.3.2)  | framing/path authoring
```

- **Domain** answers *what are we authoring*: the world's contents (Scene) vs
  how the visitor moves through it (Camera).
- **View** answers *how we author it*: top-down where/connected (Plan) vs
  spatial how-it-looks (3D).
- The domain switch changes **tooling context** (sidebar, inspector, timeline,
  tool rail); the view switch changes **spatial representation and
  view-specific affordances** (e.g. X/Z-only anchor drag in Camera Plan vs full
  XYZ in 3D).
- Symmetry of structure, not of features: `Scene → Plan` keeps today's layout
  authoring; there is **no** scene-content top-down surface (workspace-design
  §5.6).

S10.3.1 itself delivers the shell and the navigation matrix. The Camera → Plan
**cell** is a read-only stub here (layout backdrop, no camera overlay); the
camera graph surface lands in S10.3.2 (B2).

## 3. Shell contract — successor invariants (authoritative)

In any conflict between mockups and this specification, these invariants govern:

1. **Domain×view matrix shell.** The app bar contains two distinct segmented
   controls, never one combined 4-tab bar:
   - Domain: `[ Scene | Camera ]` — primary, **always visible**, never
     unmounts or reorders.
   - View: `[ Plan | 3D ]` — per domain, **fixed order everywhere** (never
     `[3D | Plan]`), always visible. The view switcher must not unmount, jump,
     or swap meaning when the domain changes.
2. **Cell ownership.** `Scene → Plan`: layout authoring (rooms/walls/anchors) +
   layout inspector. `Scene → 3D`: scene-object authoring + scene inspector.
   `Camera → Plan`: camera-graph authoring over a read-only layout backdrop
   (S10.3.2; stub in S10.3.1). `Camera → 3D`: framing / path authoring
   (today's Camera viewport). No cell exposes another domain's mutation
   surface.
3. **Domain switch is chrome-only.** Switching `Scene ↔ Camera` creates no
   history entry, no selection write, no document/dirty change, no Canvas
   remount (in 3D, `H13DView` stays mounted and receives the new domain as its
   `context` prop), and no layout-state change. It restores the target domain's
   last view (§5) and its preserved selection (§4).
4. **View switch is surface-only.** Within a domain, only the center surface
   and view-specific tools/inspector sections change. Camera domain:
   **Sequence panel, camera timeline, and camera selection persist** across
   Plan ↔ 3D. Scene domain: layout selection persists across Plan ↔ 3D
   (selected room/wall stays highlighted in 3D; read-only card in Plan), and a
   scene-object selection persists across 3D ↔ Plan (read-only in Plan).
5. **Toolbar ownership (no duplication).** Each action appears in exactly one
   place per cell. 3D cells: the viewport toolbar owns transform modes (Scene
   `Select | Move | Rotate | Scale | Local/World | Snap | View`; Camera
   `Select | Move | Rotate | Add camera | View` — Scale hidden, View menu rows
   per S10.1). Plan cells: 2D toolbars own modes (`Scene → Plan`: the existing
   layout toolbar; `Camera → Plan`: `Select | Add camera | Connect | View` —
   B2). A **left context tool rail** is reserved per (domain, view) for tools
   not already on the toolbar; in S10.3.1 the rail is an empty slot, and no
   action may appear in both the rail and a toolbar.
6. **Camera-domain timeline.** `EditorCameraTimelineFrame` keeps full-width
   ownership of `grid-area: bottom`. It mounts for the **Camera domain in both
   views** (supersedes S10.1 invariant 3). The Scene domain never mounts it;
   Scene keeps the slim status strip.
7. **Plan mutation boundary.** Only the `Scene → Plan` cell authors layout
   geometry. `Camera → Plan` reuses the **same Scene Plan render model** as a
   read-only-but-hit-testable spatial backdrop — no layout selection, no
   layout mutation, and (from S10.3.2) no framing content. No cell mutates
   another domain's state.
8. **One camera selection across Plan/3D.** Camera selection (nodes,
   connections, interior anchors) is a single shared slot; switching views
   never changes it, and a selected anchor/node keeps its identity when
   switching to Camera → 3D. Domain switches never clear it. On return to the
   Camera domain, the preserved selection is restored **when still valid**;
   otherwise it degrades per the existing S10 child-selection rules (e.g. a
   deleted node degrades to its nearest ancestor).
9. **Relic isolation.** `/museum/editor` remains frozen (S10.1 invariant 4,
   unchanged). Every shared-component change is guarded via the H1 context
   props.
10. **No new store or document.** `EditorViewState` remains the single pure
    state holder (§5). The legacy store mapping goes through the existing
    `currentWorkspace` seam; view-level gating reads `EditorViewState`, never
    `currentWorkspace` (which is now domain-level only — see §5).

## 4. Selection memory contract

Today the editor keeps three untouched selection slots
(`EditorSelectionStore.workspace` scene, `EditorSelectionStore.navigation`
camera, `LayoutInteractionState.selection` layout) resolved to one active
domain by `deriveActiveSelection` with the global priority
**layout > scene > camera**. Under the matrix this priority is wrong: in the
Camera domain a stale layout selection must not win the inspector, and in the
Scene domain a stale camera selection must not either. The contract:

- **Domain-gated resolution.** `deriveActiveSelection` (in
  `active-editor-selection.svelte.ts`) gains the shell's current domain as an
  input. The active domain's slot resolves; preserved slots in other domains
  stay untouched and **inert** (visible in the tree, not driving the inspector
  or toolbar). The three slots remain the single source of truth — no new
  selection store.
- **Within the Scene domain:** `Scene → Plan` activates the **layout** slot;
  `Scene → 3D` activates the **scene** slot. Switching views never clears
  either slot, so a selected room/wall stays selected (highlighted in 3D) and
  a selected object stays selected (read-only card in Plan) — matching today's
  behavior, which the matrix preserves rather than rewrites.
- **Within the Camera domain:** the **camera** slot is active in both views.
  `Camera → Plan` interaction (S10.3.2) must route through the camera
  selection paths (`selectNavigationNode` / connection / anchor selectors),
  never through layout selection — the hit-testable backdrop (§3 invariant 7)
  must not commit a layout pick, or the old `layout > scene > camera` reducer
  would detach the camera selection the user just made.
- **Degradation.** On domain return, restore the preserved selection when
  valid; otherwise degrade per the existing S10 child-selection rules.
- **History.** Domain and view switches write no history and no selection
  domain changes (B1 exit criterion).

## 5. State model and navigation semantics

`EditorViewState` (`apps/museum/src/lib/editor/h1/editor-view-state.svelte.ts`)
gains a domain axis with per-domain view memory:

```ts
type EditorDomain = 'scene' | 'camera';          // replaces Editor3dContext
domain = $state<EditorDomain>('scene');
views  = $state<{ scene: EditorViewMode; camera: EditorViewMode }>
         ({ scene: 'plan', camera: '3d' });      // per-domain view memory
```

- `active3dContext` and `Editor3dContext` are retired from the H1 shell
  (the relic's own state is untouched). All H1 call sites move to
  `domain` / `views[domain]`.
- Same-value switch = no-op, as today. Domain switch restores
  `views[targetDomain]`; view switch writes only `views[domain]`.
- **Store mapping** (`H1EditorApp`'s sync effect):

  | Cell | `store.currentWorkspace` | `layoutInteraction.viewMode` |
  |---|---|---|
  | Scene → Plan | `'layout'` | `'plan'` |
  | Scene → 3D | `'scene'` | `'3d'` |
  | Camera → Plan | `'camera'` | `'3d'` (layout tools off; surface read-only) |
  | Camera → 3D | `'camera'` | `'3d'` |

  `currentWorkspace` becomes **domain-level** (both Camera cells report
  `'camera'`), so every view-level gate must read `EditorViewState`. Audit in
  S10.3.1.0: H1 components already gate on explicit `context` props
  (`H13DView`, `EditorViewportToolbar`) or on `viewState`; the remaining
  `store.currentWorkspace === 'camera'` reads in shared editor stores
  (`selection-actions.svelte.ts`, `navigation-graph-mutator.svelte.ts`) stay
  correct because Camera Plan *is* the camera domain — they need no change,
  only regression coverage.
- **Center-surface mount** (`H1EditorApp`): `scene+plan` → `H1PlanView`
  (editable); `camera+plan` → `H1PlanView` in **read-only mode** (§6.5, the
  S10.3.1 stub); either 3D view → `H13DView {context: domain}` (Canvas stays
  mounted across domain switches).
- **App bar** (`H1AppBar`): domain switcher always visible; per-domain view
  switcher always visible; the `viewMode === '3d'` gate on the Scene/Camera
  control is removed; action-row entries key on the active cell (Preview Flow
  in Camera domain; Preview Museum in Scene → 3D, as today).
