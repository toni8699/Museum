## Goal

Rework H1 editor navigation into a clear three-level authoring model:

```text
Plan  ↔  3D
           ├─ Scene
           └─ Camera
```

- **Plan** is a dedicated 2D layout workspace for rooms, walls, openings, anchors, and other layout geometry.
- **3D** is the bridge into spatial editing and preserves the user's scene, camera, selection, and viewport context.
- **Scene** is the focused 3D workspace for hierarchy/assets, scene-object transforms, materials/properties, lighting, and layout refinement.
- **Camera** is the focused 3D workspace for camera nodes, guided tours, connections, path/framing helpers, timing, playback, and the camera timeline.

The product should feel like **one editor with focused workspaces**, not several disconnected tools. Switching workspaces changes chrome and emphasis without loading another project state, creating history, resetting selection, or visually rebuilding the whole editor.

Implementation remains based on the existing H1 state model: Scene and Camera are still represented by `EditorViewState.active3dContext`. In product/UI language they are **workspaces**; in state architecture they remain **3D contexts**. This distinction avoids creating a second document or workspace store simply to support the new presentation.

The frozen `/museum/editor` relic remains unchanged.

## Amendment — camera-node order model (product review, 2026-08-17)

**Status:** Approved direction — supersedes the "Guided Tour vs Free Nodes"
product language in the Camera workspace for H1. Implementation is deferred to
the S10.1.3/S10.1.4 increments below; a speculative first pass (timeline-panel
repair UI + `findSimpleGuidedCycle`) was reverted 2026-08-17 as overengineering
that did not fix the live failures (the actual fixes: the two-node guided seed
in the connect mutator, the `EditorCameraTimelineDots` edge-key fix, and the
H1 Escape cascade fix — see the handoff). The plan below is the target, not
shipped state.

> **Superseded by S10.2 (Camera Flow model, 2026-08-17).** The S10.2 plan
> ([`2026-08-17-graphics-h1-s10.2-camera-flow-model.md`](./2026-08-17-graphics-h1-s10.2-camera-flow-model.md))
> lands before this slice and replaces the closed-loop language below: the
> main route is an **open chain** by default (append needs exactly one edge,
> insert needs at most one), the "path must close" / Close-loop requirements
> are removed from persistence, and **Loop playback is a manual authoring
> choice** — the user connects the tail back to the head, closing the order
> links with a real authored return edge (no synthesized playback wrap). This
> slice's sidebar/timeline empty-state increments must be reworked against the
> S10.2 model instead of `findClosableGuidedChain` / `closeGuidedTourLoop`.
> The "3+ nodes must close" bullet below is obsolete.

### Why

The authoring surface should not ask the user to reason about two internal
node classes. There is one camera graph; order comes from connections:

```text
Node 1 → Node 2 → Node 3 → … → back to Node 1
```

"Guided Tour" and "Free Nodes" describe the internal reciprocal-link state
(`nextNodeId` / `previousNodeId`), not the user's mental model. The Camera
workspace should present **Camera nodes** as one ordered path:

- **Order is the connection sequence.** Node 1 → Node 2 means the camera moves
  from node 1 to node 2; the ordered path is the tour. A node placed but not
  yet linked into the path is simply "not in the order yet", not a different
  class of node.
- **Order is editable.** Reorder via drag or move buttons; **a new node can be
  inserted at any position** in the path (existing `insertNodeIntoGuidedTour`
  + the guided-gap drag/insert affordance — make it a first-class "Insert
  after Node N" control in the Camera sidebar, not only drag-and-drop).
- **Preview plays the ordered path.** `canStartTourPreview` stays the
  authoritative gate. For 3+ nodes the path must close (last → first return
  edge); exactly two connected nodes need only the explicit order written
  (one undirected edge already covers both directions).
- **Internal mechanics are unchanged.** The reciprocal links, pure
  `findClosableGuidedChain`, and atomic `closeGuidedTourLoop()` /
  `setGuidedTourOrder()` mutators remain the implementation; only the UI
  language changes.

### Copy changes to apply

- **Timeline empty state (S10.1.4 target).** `EditorCameraTimelinePanel`
  should stop showing the dead-end "Guided timeline unavailable" and instead
  speak node order with repair actions. (A first attempt at this was reverted;
  keep it small: reuse the existing `setGuidedTourOrder` mutator and the
  `findClosableGuidedChain` predicate, and only add closed-cycle detection if
  the panel actually needs it.)
- **Camera sidebar (deferred to S10.1.3).** Section headers become
  "Camera nodes" (ordered path) instead of "Guided Tour" / "Free Nodes";
  the un-ordered remainder reads "Not in order yet" instead of "Free Nodes";
  every node row carries its sequence number and the insert affordance.
  The relic keeps its legacy labels unchanged.

## Sequence boundary

S10.1 starts only after S10's context prop, context-safe helper/timeline gates,
pure Close-loop predicate, atomic `closeGuidedTourLoop()` mutator, and
selection-domain contracts are complete. This slice is the visible product
recomposition: it consumes those technical seams for the dedicated sidebar,
toolbars, bottom timeline presentation, and transitions rather than extending
the relic-era flags or creating parallel camera state.

### Fallback scope split

S10.1 is planned as one product slice, but its implementation may be split
internally if the combined UI surface starts to balloon:

1. **Functional workspace composition:** sidebar, context-specific toolbars,
   Place Camera relocation, and Camera timeline/sidebar wiring.
2. **Behavioral polish:** workspace transitions, conditional Close-loop empty
   state, selection persistence, and keyboard-focus handling.
3. **Design-system polish last:** CSS tokens, typography, icon treatment, panel
   geometry, spacing, and visual QA refinements.

The third pass is deliberately last and must not block the functional or
behavioral work; it may continue using the existing styles while the first two
passes stabilize. This is an internal fallback, not a change to the approved
S10 → S10.1 dependency order.

## Incremental delivery plan

S10.1 remains one named product slice, but it must be executed as the ordered
increments below. Each increment is independently reviewable and must leave the
editor usable; a future engineer or AI agent may expand an increment into a
separate implementation brief without reopening the S10 technical contracts.
The existing numbered implementation steps later in this document are the
acceptance detail for these increments.

### S10.1.0 — Dependency, visual inventory, and implementation brief

**Purpose:** remove dependency ambiguity before changing the shell.

- Inventory the existing H1 components, current inline SVGs, CSS tokens, and
  route/bundle boundaries; record which icons are standard UI actions and which
  are domain-specific artwork.
- Add `lucide-svelte` to `apps/museum/package.json` (and the workspace lockfile)
  for standard editor UI icons. Do not add a second icon package or an icon
  font. Use a Lucide component whenever the icon exists and is importable; only
  use custom inline SVG when Lucide has no suitable icon or the icon cannot be
  imported as a component.
- Keep the existing system font stacks for the first pass; no font dependency
  is required to satisfy this specification. If visual QA later proves that a
  bundled font is necessary, propose `@fontsource/inter` for UI text and
  `@fontsource/jetbrains-mono` for technical values as a separate, editor-only
  typography increment. Do not check in raw font files or add either package
  speculatively.
- Define the visitor-bundle check before importing any UI library: editor-only
  chunks may contain Lucide (and any explicitly approved font package), while
  the visitor route must contain neither those imports nor editor-only icon
  assets.

**Deliverable:** a short implementation brief listing exact icon imports,
font decision, affected components, purity assertion, and visual acceptance
screenshots. No shell redesign belongs in this increment.

### S10.1.2 — Scene workspace composition

**Purpose:** finish the low-chrome scene context without camera affordances.

- Keep the existing Hierarchy / Assets sidebar and scene transform tools.
- Keep the explicit Scene View menu with Ceiling only.
- Keep camera inspector content selection-driven when a camera selection is

### S10.1.3 — Camera sidebar and camera toolbar

**Purpose:** move camera authoring entry points into the Camera context.

- Replace the shared Scene sidebar presentation with the dedicated Camera
  sidebar over the existing tree, selection, and graph APIs.
- Relocate Place Camera from the app-bar action row into the Camera toolbar;
  keep `beginCameraPlacement()` and pending-command behavior unchanged.
- Keep the Camera sidebar's numbered Guided Tour list as the concrete authored
  node order. The second-node placement flow seeds `[existing, new]` and must
  make the two-node preview available immediately; an arbitrary two-node graph
  gets an explicit `setGuidedTourOrder` action rather than a duplicate edge.
- Compose the Camera toolbar as `Select | Move | Add camera | View`; keep
  Nodes / Paths / Framing inside View and use Lucide for standard icons.
- Hide Scale, scale-chain, and misleading Rotate controls for camera targets.

**Camera Flow sidebar — Sequence Inspector and Unused tray (S10.2 UI zones).**
Builds on the S10.2 model (open chain, derived loop); this replaces the
numbered Guided Tour list language with:

- **Sequence Inspector:** the ordered-path list with sequence numbers, a
  per-transition timing row (duration + easing per transition), and the
  derived loop row rendered from the S10.2 distinct-connection test:
  `Loops via: [tail] → [head] (duration) [Disconnect Loop]`, or
  `Stops at [tail] [+ Connect to [head]]` when no distinct closing record
  exists. A two-node pair never renders a loop row. `[Disconnect Loop]`
  deletes the closing connection (one history entry); `[Connect to [head]]`
  starts the ordinary connect flow.
- **Unused Connections tray:** under Connections/Advanced, an accordion of
  retained authored curves not on the current path, each with
  [Re-attach] [Delete]; Re-attach routes through insert/reorder, Delete is a
  plain connection deletion.
- **Viewport:** inactive connections render as desaturated dashed splines with
  a View-menu toggle (alongside Nodes / Paths / Framing).
- All copy comes from the S10.2 mutation microcopy contract; no Close-loop
  language.

**QA round (2026-08-17) — rotate is a real gap, decide inside this slice.** The
user asked for a camera rotate affordance; the toolbar Rotate is greyed because
`CAMERA_GIZMO_POLICY` is translate-only (S7 parity). Rotating a camera node
*is* moving its look-target around the eye — the target handle exists but is
undiscoverable. Decision: (a) minimal — keep the translate-only gizmo, add an
**Aim / look-at** control in the camera inspector that orbits `cameraTarget`
around `position` by yaw/pitch (pure `editor-camera-view` math, one history
entry), or (b) full — teach `camera-gizmo-adapter` a rotate mode that maps the
rotate gizmo to a target-orbit session. Either lands before S10.1 sign-off;
prefer (a) for scope and testability.

**QA round (2026-08-17) — placement workflow.** The user wants "place camera →
done; place another → done; click camera 1 → connect → pick camera 2 from the
sidebar" — i.e. **standalone placement for every node** and explicit
connect-after. The current second-node connect-pending-node contract (atomic
first-edge commit, cancel discards) is pinned by tests; rework it inside this
slice as: place commits standalone → node is "not in the order yet" →
`Connect to another node` in the inspector/toolbar starts `connect-existing`.
The two-node guided seed (already shipped in the connect mutator) and the
pre-existing `setGuidedTourOrder` mutator remain the convergence paths for
two-node graphs.

**Exit:** every camera authoring entry point is reachable in Camera, no camera
UI is duplicated in Scene, the Sequence Inspector and Unused tray render the
derived loop and retained connections with no Close-loop language, and the
relic route is unchanged.

### S10.1.4 — Timeline and guided-cycle completion UI

**Purpose:** connect the existing bottom frame to a truthful guided-tour state.

- Preserve `EditorCameraTimelineFrame` as the full-width `grid-area: bottom`
  strip with its horizontal resize handle and header chrome; never move it into
  the sidebar.
- Replace the dead-end timeline message with the S10.2 derived state, never
  Close-loop language: when the distinct-connection test holds, render the
  loop readout `Loops via: [tail] → [head]`; when the path is open, render
  `Stops at [tail]` with `[+ Connect to [head]]`. A two-node pair never shows
  a loop row. A missing transition renders the stop-and-name message from the
  S10.2 microcopy contract.
- Call only the S10/S10.2 graph mutators, retain `canStartTourPreview`, and
  verify one undo entry; the loop readout is derived, never a mutation.

**QA round (2026-08-17) — two-node timeline render regression, fixed.**
`EditorCameraTimelineDots` keyed edges by `edge.connectionId` alone; a
2-node cycle reuses its one connection for both directions, so the forward and
return edges collided and Svelte threw `each_key_duplicate` every render — the
thrown flush aborted the gizmo detach effect, leaving TransformControls
attached to an unmounted helper root (`The attached 3D object must be a part of
the scene graph` spam, drag rotated the orbit instead of moving the node).
Edges are now keyed `\`${connectionId}:${direction}\``; the exit criteria must
keep asserting that a 2-node cycle renders **two** distinct direction edges.
Also fixed in the same round: the H1 shortcut cascade's W/E/R/T branch
swallowed plain Escape, so the connect-pending prompt could not be cancelled
(`cancelPendingNavigation` now runs at the top of the mode-key branch).

**Exit:** the timeline readout reflects the derived distinct-connection test
with no Close-loop action; a two-node pair never loops and renders both
direction edges with distinct keys; missing transitions stop playback at the
last valid node with the named pair.

### S10.1.5 — Selection, inspector, and Plan bridge

**Purpose:** complete cross-context selection behavior without new stores.

- Reuse `ActiveEditorSelection` and the S10 rule: context controls helper,
  tool, and timeline chrome; active selection domain controls inspector
  content.
- Keep preserved camera selection inspectable in Scene when valid, and make it
  read-only in Plan with a direct Switch to 3D message.
- Add focus handoff when a switch unmounts the focused control; never steal
  focus by auto-focusing the viewport.

**Exit:** selection survives supported switches, no stale gizmo target remains,
and Plan exposes no scene/camera mutation path.

### S10.1.6 — Motion, reduced motion, and interaction hardening

**Purpose:** add coordinated motion only after the static composition works.

- Animate shell/frame content rather than remounting the central Canvas.
- Implement the specified 180–220 ms Scene ↔ Camera and 220–280 ms Plan ↔ 3D
  transitions, with no delayed state mutation.
- Add the reduced-motion path (instant layout or <= 80 ms opacity), focus-ring
  behavior, rapid-switch cancellation, and playback/interaction guards.

**Exit:** transitions are interruptible, accessible, and cannot expose stale
camera controls during a switch.

### S10.1.7 — Design-system polish and release hardening

**Purpose:** apply visual tokens after behavior is stable.

- Add scoped editor tokens, geometry, spacing, typography decisions, Lucide

- Run visual QA at the listed viewport sizes and record deviations as explicit

- Run the visitor-bundle purity check, full tests, `svelte-check`, production

### Detailed-specification handoff template

Before implementing any increment, the next engineer/agent should add a brief
with: (1) user outcome and out-of-scope behavior, (2) source components and
existing APIs to reuse, (3) new props/state/dependencies, (4) mount/unmount and
selection semantics, (5) exact acceptance tests and manual scenarios, (6)
relic/Plan/visitor boundaries, and (7) rollback or fallback split if the
increment expands. This keeps the broad S10.1 vision decomposable without
creating parallel state or silently weakening S10 contracts.

## Visual & Functional Invariants (Authoritative)

In any conflict between the concept sketches/mockups and this specification,
the following invariants govern:

1. **Persistent dual-switcher shell (spec text authoritative).** The app bar
   contains two distinct segmented controls, never one combined 4-tab bar:
   - Primary: `[ Plan ] [ 3D ]` (always visible, left-anchored);
   - Secondary: `[ Scene | Camera ]` (mounts adjacent to the primary control
     only when `viewMode === '3d'`).
   `[ Plan ] [ 3D ]` must never unmount, jump, or be replaced when switching to
   the Camera workspace.

2. **Context-specific viewport toolbars and View menus (no duplication).**
   - Scene workspace: viewport toolbar `Select | Move | Rotate | Scale |
     Local/World | Snap | View`; the View dropdown exposes **Ceiling only** and
     omits every camera-helper row.
   - Camera workspace: viewport toolbar `Select | Move | Add camera | View`;
     `Scale`, the scale-chain toggle, and the relic `Rotate` mode are
     unmounted; `Add camera` moves from the app-bar action row into this
     toolbar; the View dropdown exposes **Node handles**, **Tour paths**, and
     **Framing & FOV** only. Top-level helper buttons are not duplicated on the
     toolbar.

3. **Timeline bottom frame.** `EditorCameraTimelineFrame` retains full-width
   ownership of `grid-area: bottom` beneath the sidebar, viewport, and
   inspector. It mounts strictly when
   `viewMode === '3d' && active3dContext === 'camera'`.

4. **Relic isolation.** `/museum/editor` remains frozen. Every shared-component
   change must be guarded via the H1 workspace context prop.

## UX mental model

### Workspace relationship

```text
┌─────────────── persistent editor shell ────────────────┐
│ Museum editor                           Undo / Project │
│                                                        │
│             Plan  ↔  3D                               │
│                       ├─ Scene                         │
│                       └─ Camera                        │
└────────────────────────────────────────────────────────┘
```

Rules:

1. **Plan ↔ 3D is the primary mode switch.**
2. **Scene / Camera are sub-workspaces of 3D.** They are not shown as peers of Plan when Plan is active.
3. Entering 3D restores the most recently used 3D workspace (`scene` or `camera`).
4. Scene ↔ Camera is a context-only switch: with no pending command, active interaction/transaction, or playing preview, it creates no document, history, or selection-domain change. Existing session effects remain intentional: pending navigation is cancelled, leaving Camera stops preview, and timeline expansion preferences are restored.
5. Plan ↔ 3D is also view-only: layout/scene documents stay loaded and current selection is preserved where the target workspace can represent it.
6. Workspace-specific chrome should appear/disappear through a short coordinated transition rather than popping unrelated panels into the UI.

### Why this model

- **Plan:** "draw / shape the space."
- **Scene:** "place / edit what is in the space."
- **Camera:** "author how the visitor moves through the space."

The user never needs to reason about internal document boundaries or camera graph ownership.

## Workspace specifications

## 1. Plan workspace

### Purpose

Layout-only authoring of architectural geometry and structural navigation data.

### App-bar state

```text
Museum editor     [ Plan ] [ 3D ]                         UNSAVED  Undo  Redo  Project ▾
```

- `Plan` active.
- `3D` is the only adjacent mode entry.
- Do **not** show Scene / Camera tabs while Plan is active.
- Use a clear **Switch to 3D** affordance in the left sidebar footer when relevant.

### Layout

```text
┌──────────────┬────────────────────────────────────┬───────────────┐
│ hierarchy    │ 2D plan canvas                     │ inspector     │
│              │                                    │               │
│ rooms        │ room/wall/opening tools            │ contextual    │
│ architecture │ dense metric grid                  │ read-only     │
│ scene refs   │ pan / zoom / snap                  │ notices for   │
│ tour refs    │                                    │ non-layout    │
└──────────────┴────────────────────────────────────┴───────────────┘
```

#### Left sidebar

Keep the unified project tree because Plan needs spatial/document context:

- Rooms
- Architecture
  - walls
  - bend anchors
  - doors/openings
- Scene object references (visible but not transform-editable in Plan)
- Camera Tour / Guided Tour / Free Nodes as references only where already supported

A selected non-layout item may survive from 3D, but mutation controls must remain unavailable.

#### Center canvas

Toolbar order:

```text
Select | Rect room | Polygon room | Snap 0.25m | Grid | Tour | …
```

Canvas behavior:

- orthographic 2D grid;
- rulers in meters along top and left edges;
- room/wall geometry remains high contrast against the grid;
- selected anchors use gold selection treatment;
- openings and bend handles remain directly manipulable;
- middle-drag pans;
- mouse wheel zooms;
- grid/snap state stays visible in toolbar and bottom status text.

#### Right inspector

Plan is layout-only. When selection belongs to Scene or Camera domain, show a prominent read-only information card:

> **Read-only in Plan**  
> This selection is preserved across Plan ↔ 3D. Switch to 3D to edit it.

Do not show disabled full editing forms when a compact read-only message is enough.

Session-only viewport controls such as Camera pan/grid visibility and preview Lighting may remain here if they do not mutate `project.scene`.

### Plan mutation boundary

`H1PlanView` exposes no control that writes camera or scene-object authoring state. Read-only overlays may remain, but all mutations are contract-tested out.

## 2. 3D shell / bridge

3D is not a third fully separate editing surface. It is the shared spatial shell that hosts either Scene or Camera workspace.

### App-bar state

```text
Museum editor     [ Plan ] [ 3D ]    [ Scene | Camera ]   UNSAVED  Undo  Redo  Project ▾
```

When `3D` is active:

- reveal the secondary `Scene | Camera` segmented control;
- preserve the primary Plan / 3D position so the user's navigation model stays stable;
- never duplicate Scene / Camera elsewhere in the header.

### State model

```ts
viewMode: 'plan' | '3d'
active3dContext: 'scene' | 'camera'
```

Expected navigation:

```text
Plan → 3D        restores last active3dContext
3D → Plan        remembers active3dContext
Scene → Camera   changes only active3dContext
Camera → Scene   changes only active3dContext
```

## 4. Camera workspace

### Purpose

Dedicated camera-motion authoring surface inside the shared 3D shell.

### Layout

```text
┌──────────────────┬───────────────────────────────┬──────────────────┐
│ Camera sidebar   │ 3D viewport + path overlay    │ Camera inspector │
│                  │                               │                  │
│ Guided Tour      │ camera nodes                  │ node/connection  │
│ Free Nodes       │ paths                         │ motion/framing   │
│ Connections      │ framing / safe area           │ timing           │
├──────────────────┴───────────────────────────────┴──────────────────┤
│ Camera timeline / playback / tracks                                 │
└──────────────────────────────────────────────────────────────────────┘
```

### Left sidebar

The Camera workspace owns a dedicated sidebar. Do not show `Hierarchy | Assets`
tabs here. The sidebar owns the tour tree and camera tools; the timeline stays
in the full-width bottom strip described below. A preserved camera selection
may still keep camera inspector content visible in Scene, but that does not
bring camera helper/tool/timeline chrome into Scene.

Sections (see the camera-node order-model amendment above — the split below
is legacy naming; the sidebar presents one ordered **Camera nodes** list):

1. **Camera nodes (ordered path)**
   - the ordered path — Node 1 → Node 2 → … — with sequence numbers and a
     selected-node highlight using the global selection color;
   - drag/reorder only if existing route semantics support it, plus explicit
     move controls;
   - **Insert after Node N** affordances so a new node joins the order at any
     position (reuses `insertNodeIntoGuidedTour`; drag-drop is an alternative,
     not the only path).
2. **Not in order yet** (previously "Free Nodes") — nodes present in the
   graph but not linked into the path; each row offers an insert action.
3. **Connections**
4. Contextual add actions (`Add camera`, `Add connection`) where supported.

The sidebar is a view over the existing `NavigationSelection` and route graph; no new selection store or graph. It calls the S10 selection paths and the S10 `closeGuidedTourLoop()` facade rather than implementing graph eligibility locally.

### Viewport

Always prioritize path legibility over scene editing chrome.

Visible camera-authoring overlays may include:

- camera nodes;
- connection/path curves;
- direction indicators;
- selected camera frustum;
- target/look-at helpers;
- framing/safe-area guide;
- optional path control points when editing a smooth curve.

Unrelated scene transform affordances should be visually suppressed.

### Camera toolbar

Recommended order:

```text
Select | Move | Add camera | View
```

The `Nodes` / `Paths` / `Framing` toggles live exclusively inside the Camera
View menu (invariant 2); they are not duplicated as top-level toolbar buttons.

Rules:

### Guided-cycle empty state

> **Superseded (2026-08-17, S10.2).** The Close-loop states below are replaced
> by the derived loop readout (Sequence Inspector row, S10.1.3) and the
> timeline empty state (S10.1.4), per the S10.2 locked-architecture spec and
> mutation microcopy contract. This section is retained only as history.

**Implemented (product-review amendment).** Replace `Guided timeline
unavailable` with a state derived from S10's pure
`findClosableGuidedChain(document)` predicate; do not infer eligibility from a
selected node or from `getCameraTimeline() === null` alone. Copy uses the
camera-node order model (Node 1 → Node 2), not "guided tour" jargon.

When the graph is exactly two connected nodes with no authored order, render
the concrete order and make the no-new-edge mutation explicit:

```text
Two camera nodes are connected
Preview follows the node order once it is set.
Order: [first node] → [second node]

[Set order]
```

The action calls `setGuidedTourOrder([first, second])`, writes reciprocal links,
and immediately enables the existing preview gate. The default order for the
second-placement flow is existing destination first, newly placed node second.

When the graph has three or more nodes and the predicate returns a candidate,
render the candidate's deterministic ordered endpoints by label and make the
return-edge mutation explicit:

```text
The camera path is open — preview needs to return to the first node
Chain: [first node] → … → [last node]
Close loop will add: [last node] → [first node]

[Close loop]
```

The ordered chain starts at the endpoint appearing first in document order, so
`[last node] → [first node]` is the exact return edge that S10 will add. The
button calls S10's `closeGuidedTourLoop()` mutator, which adds that edge and all
reciprocal links in one `scene` history entry, selects the new connection, and
posts confirmation status.

When the graph is already a **closed simple cycle** (N ≥ 3 nodes, exactly N
connections, every node degree two, no parallel edges, no order links yet —
the user drew the closing edge by hand), there is no missing edge, so Close
loop must not be offered. Render the concrete cycle order and make the
links-only mutation explicit:

```text
The camera path is already a closed loop — Preview just needs the node order
All connections exist; the order links just need to be written.
Order: [first node] → … → [last node] → back to [first node]

[Set order]
```

The button calls `setGuidedTourOrder(cycleOrder)` (the pure
`findSimpleGuidedCycle(document)` walk, pinned to entrance-start when present)
and immediately enables the existing preview gate without creating any edge.

When none of the two-node order, closed-cycle, or 3+ open-chain cases
apply—including for a stray node, branch, parallel edge, second component,
partial link, or any other ambiguous graph—do not render either action or
claim that only the return edge is missing. Render a diagnostic issue list
that names the concrete blockers and the repair for each:

```text
The camera path can't be previewed yet
• 2 nodes carry a partial order link — reset the order for those nodes first.
• 1 duplicate connection — delete the extra edge between the same two nodes.
• 1 node is not connected — select and connect it into the line.
• 1 node has more than two connections — remove the extra edge.
```

The UI must not call `connectNavigationNodes()` directly or implement a second
graph predicate. `findSimpleGuidedCycle` and `findClosableGuidedChain` live in
the graph module and are unit-tested; the panel only consumes them.
`canStartTourPreview` remains authoritative; `Close loop` only makes the
existing gate legible and never invents nodes or an entire tour.

## Workspace transition behavior

The main UX requirement is that switching feels like **one workspace reshaping itself**, not a full page swap.

### Persistent during every switch

Never animate/remove:

- app identity / project name;
- primary Plan / 3D mode control;
- save/dirty state;
- Undo / Redo;
- Project menu;
- central 3D canvas instance when switching Scene ↔ Camera.

### Scene ↔ Camera transition

Duration: **180–220 ms** total.

Use coordinated panel transitions:

1. Existing sidebar content fades/slides **8–12 px** outward.
2. New sidebar content fades/slides into the same panel frame.
3. Inspector swaps contents inside the same fixed right-column frame.
4. Camera timeline expands from the bottom using height + opacity; Scene switch collapses it.
5. Viewport should resize smoothly rather than remount.
6. Camera helpers fade in/out over **120–160 ms** after the layout starts moving.

Suggested easing:

```css
cubic-bezier(0.2, 0.8, 0.2, 1)
```

No bounce or spring animation. This is a professional editing tool, so motion should confirm hierarchy rather than draw attention to itself.

### Plan ↔ 3D transition

Duration: **220–280 ms**.

- Keep shell/header stationary.
- Crossfade the 2D plan canvas and 3D viewport within the center frame.
- Preserve selected item where supported.
- Secondary Scene / Camera switcher appears only after 3D becomes active; fade/slide it **4–8 px** from the primary 3D tab rather than popping in.
- When returning to Plan, secondary switcher disappears but `active3dContext` remains remembered.

### Reduced motion

When `prefers-reduced-motion: reduce`:

- remove translations and height tweening;
- use instant layout change or <= 80 ms opacity only;
- preserve all state behavior.

### Workspaces are presentation; documents stay unified

- No new store.
- No new document domain.
- No new camera fields.
- Scene and Camera remain `active3dContext` values.
- Plan remains `viewMode === 'plan'`.
- Workspace switching is presentation/state selection only.

- Camera helper visibility controls appear only in Camera.
- The View menu is context-specific: Scene exposes **Ceiling only**; Camera
  exposes **Node handles**, **Tour paths**, and **Framing & FOV** only.
- Timeline/playback mounts only in Camera.
- `Add camera` moves from global app bar into Camera viewport toolbar.
- Preview Tour stays app-bar-level.
- Camera workspace hides Scale and scale-chain UI.
- Adapter stays translate-only.

### Camera workspace owns its sidebar

- `Hierarchy | Assets` are Scene workspace chrome.
- Camera workspace renders dedicated Guided Tour / Free Nodes / Connections surface.
- It reuses existing route graph + selection paths.
- No forked camera selection state.

### Guided-cycle completion is guided, not silently gated

- Empty state names the missing closed-loop requirement.
- `Close loop` appears only when S10's pure `findClosableGuidedChain(document)`
  predicate returns an unambiguous complete 3+ node simple path: exactly `N - 1`
  unique adjacent connections, no branch/parallel/partial or existing guided
  links, no extra component, and exactly one missing last-to-first return edge.
- Exactly two connected nodes use a separate concrete-order path: the second
  placement seeds `[existing, new]` reciprocal links in one scene transaction;
  an arbitrary two-node graph exposes `setGuidedTourOrder` and never creates a
  duplicate return edge.
- S10's dedicated `closeGuidedTourLoop()` operation performs the change as one
  `scene` history entry, writes the reciprocal guided links, selects the new
  return connection, and posts confirmation status.
- No node or route generation; the UI does not call `connectNavigationNodes()`
  directly or implement a second eligibility predicate.

### Plan remains mutation-safe

- Plan can show references/overlays.
- Plan cannot mutate camera or scene-object authoring state.
- Read-only boundaries are enforced by tests, not only disabled CSS.

### Relic isolation is absolute

`/museum/editor` keeps `EditorAppBar`, `EditorLeftSidebar`, `EditorViewport`, and legacy Camera workspace behavior unchanged.
