# P20.4 (S4) — Load/runtime asset-resolution slice brief

**Date:** 2026-09-03 · **Plan:** [P20 Project Asset Registry + R2](2026-08-19-P20-Project-assets-registry-R2.md) S4

**Status:** **shipped 2026-09-04**; the owner-run P20.1 private-R2 smoke was
closed by the local live smoke (local API + local Postgres + real R2), and the
deployed round-trip below passed on the same local stack

**Baseline:** P20 S0 contract + locally complete P20.1 API, P20.2 Spatial integration, and P20.3 durable conversion

**Purpose:** make an authenticated cloud Load fetch and verify every referenced project texture before document replacement, then reuse the existing binary cache and renderer so Save → refresh → Load preserves rendered texture fidelity.

P20.4 is implemented through one staged hydration helper and the existing
`EditorApp` Load transaction. Targeted tests, the full editor suite, API tests,
static checks, builds, and visitor-bundle verification pass locally; production
R2 verification remains owner-run.

---

## 1. Outcome and cut line

For an authenticated owned project saved with durable texture references:

```text
P19 Load ProjectDocument
→ find unique /project-assets/{assetId} texture URIs
→ P20.1 registry metadata + authorized content GET
→ verify ready/type/MIME/size/SHA
→ prime BinaryTextureStore
→ replace the current project once
→ existing texture loader renders from its object URL
```

The loaded document remains byte-for-byte semantic project truth. Resolution
does not rewrite texture IDs or URIs, create history, or mark the project dirty.

Load is fail-closed and atomic when the document references a project asset:
missing/unready metadata, missing bytes, an authorization failure, or an
integrity mismatch leaves the current document, layout, selection, history,
baselines, and project identity unchanged. A project with no logical asset
references keeps the existing Load path and is not coupled to the asset-list
endpoint.

P20.4 does not add an on-demand network loader, new renderer, persistent browser
cache, background prefetch, progress UI, final Assets workspace, GLB support,
provider import, delete/GC, deduplication, or schema/version changes.

## 2. Current seams to reuse

| Surface | Existing seam | P20.4 use |
| --- | --- | --- |
| Load transaction | `EditorApp.svelte` `loadProject`, request token/controller, fingerprint and interaction guards | Extend the existing guarded replacement; do not add a second Load controller |
| Stable reference | `isProjectAssetUri` + `/project-assets/{assetId}` | Collect distinct referenced texture assets only |
| Registry/API | `ProjectApi.listAssets` + `loadAssetContent` | Obtain owned metadata, then fetch private bytes through the authenticated API |
| Validation | P20.3 ready-metadata rules, `sniffImageMime`, `registerVerifiedProjectAsset` | Require texture/upload/R2/ready metadata and verify MIME, size, sniffed type, and SHA before cache mutation |
| Runtime bytes | `BinaryTextureStore` | Reuse a matching cache entry or register verified bytes under the unchanged logical URI |
| Renderer | `createEditorSourceLoader` → `BinaryTextureStore.objectUrlFor` → current texture cache | No renderer/material/loader change; bytes exist before document replacement can mount them |
| Project replacement | `replaceProjectDocument`, layout preview install, saved baselines, selection reset | Preserve the current one-shot successful Load semantics |
| Asset context | `projectAssetContextId`, `projectAssets`, `projectAssetsStatus` | Adopt the metadata already fetched for resolution; avoid an immediate duplicate list request |

`SceneTextureAsset` remains `{ id, name, uri }`. No R2 key, API URL, metadata,
bytes, or resolution state enters `ProjectDocument`.

## 3. Decisions

### D1 — Resolve before replacement, not lazily from the renderer

After project validation and layout preview derivation, collect unique logical
URIs from `validation.project.scene.textures`. If the set is empty, continue the
existing Load unchanged.

If the set is non-empty:

1. list the selected project's assets with the existing Load abort signal;
2. match every referenced asset ID to exactly one metadata row for that project;
3. require the existing P20.3 ready predicate fields;
4. reuse a `BinaryTextureStore` entry only when fingerprint, MIME, and byte size
   match that metadata;
5. otherwise fetch and verify each missing/mismatched asset;
6. only after every reference verifies, prime the cache and perform the existing
   document replacement.

Pre-hydration is the smallest working resolution seam. The current source loader
already checks `BinaryTextureStore`; teaching it to perform authenticated fetches
would duplicate project ownership, cancellation, metadata, and integrity logic
inside rendering.

### D2 — Stage validation; do not partially mutate the live cache

Fetch missing assets sequentially with the existing project request controller.
Each asset is at most 25 MiB; sequential fetch bounds extra memory and avoids an
unbounded burst without adding a scheduler.

Use `registerVerifiedProjectAsset` with a staging callback to verify SHA without
registering bytes yet. Keep staged `{ uri, bytes, mime, fingerprint }` values
local to the Load. After all assets verify and the existing token, document
fingerprint, and interaction guards still pass, register the staged entries and
immediately replace the project.

If cache registration or replacement fails, retain only the still-current
document's texture URIs and P20.3 history aliases. No partially loaded target
asset remains as evidence that Load succeeded.

### D3 — Metadata is required; content bytes alone are insufficient

A referenced row must match:

```text
id from logical URI
+ selected projectId
+ kind=texture
+ storageKind=r2
+ sourceKind=upload
+ importState=ready
+ supported MIME
+ finite 1..25 MiB byteSize
+ non-empty SHA-256 fingerprint
```

Then content must match response MIME, byte size, sniffed MIME, and SHA. Cache
presence alone does not prove ownership or current registry readiness. Pending,
failed, procedural, built-in, cross-project, malformed, and duplicate-ID rows
cannot resolve a saved logical texture.

### D4 — One project Load owns document and asset requests

Use `projectRequestController` and `projectRequestToken` for the document,
metadata, and content requests. Starting another Save/Load, signing out,
project/session invalidation, navigation teardown, or app unmount aborts the
whole chain. Every await rechecks the request token/signal before staging,
cache registration, document replacement, or status mutation.

Do not route Load hydration through `beginProjectAssetMutation`: resolution is
part of project replacement, not an authoring mutation, and must not cancel or
publish upload retry state.

### D5 — Successful Load adopts the fetched registry snapshot

After cache prime and project replacement succeed, preserve the current Load
closeout, then set the selected project as the active asset context and install
the fetched list as `projectAssets` with status `ready`. This makes P20.3's
cloud-Save readiness predicate true immediately and avoids a duplicate list.

The existing context effect continues to refresh assets for no-reference
projects and after later project/session changes. A post-Load manual refresh may
update registry rows but must not evict bytes referenced by the current scene.

### D6 — Failure and retry behavior

| Failure point | Current project | Retry |
| --- | --- | --- |
| Project document/codec/layout invalid | unchanged | fix remote data; Load again |
| Referenced metadata missing, duplicate, or unready | unchanged | finish/recover upload; Load again |
| Content GET/auth/network failure | unchanged | restore session/network; Load again |
| MIME/size/SHA mismatch | unchanged | repair stored object/metadata; Load again |
| Request superseded or aborted | unchanged; no late writes | latest action owns state |
| Guard changes while bytes load | unchanged | retry after authoring settles |
| Cache registration/replacement failure | unchanged; staged target entries pruned | Load again |
| Successful Load | clean loaded project; selection reset once | ordinary authoring/Save resumes |

There is no partial/degraded Load and no automatic retry loop. The existing
cloud error/status surface reports the first failing asset by name or ID without
exposing an R2 key.

## 4. File work

1. `apps/editor/src/lib/editor/project-asset-load.ts` — one pure, injected
   hydration helper: collect/dedupe refs, validate metadata/cache/content, stage
   verified bytes, and return the registry snapshot plus staged entries.
2. `apps/editor/src/lib/editor/app/EditorApp.svelte` — call the helper inside
   the existing `loadProject` transaction, commit staged cache entries before
   replacement, adopt asset context on success, and prune on failure.
3. `apps/editor/tests/lib/editor/p20-s4-load-resolution.test.ts` — focused
   helper/orchestration tests.
4. Existing app contract/boundary tests only where needed to pin the wiring.

No API, migration, schema, project-model, binary-store, texture-loader,
renderer, material, visitor, relic, layout, camera, selection, or history
implementation should change. If two small local functions in `EditorApp.svelte`
remain directly testable through the helper inputs, do not add a class or store.
New component props, persistent state, packages, and dependencies: **none**.

## 5. Mount/unmount, history, and selection semantics

- Automatic boot Load (`load=1`) and explicit Project menu Load use the same
  hydration transaction.
- The old project stays mounted and interactive state stays intact until every
  target byte verifies; `cloudStatus='loading'` supplies existing feedback.
- Successful replacement keeps current behavior: replace scene/layout once,
  mark both baselines saved, reset selection once, set loaded name/version, and
  create no history entry.
- Failed, aborted, or stale resolution changes no selection, recent texture,
  material assignment, history, dirty state, baseline, project name/version, or
  active project ID.
- Cache registration creates no history. Undo/redo never fetches or mutates
  registry/R2 state.
- Project switch, sign-out, replacement, and unmount abort outstanding content
  fetches and prevent late cache/document writes. Normal cache cleanup retains
  current scene URIs plus P20.3 source aliases.
- Guest, unauthenticated, unconfigured, unsaved, or foreign projects cannot
  resolve private project assets.
- Scene Plan and Camera Plan keep their existing mount/render behavior; neither
  receives registry state or a second texture-resolution path.
- `/museum/editor` receives no project API/resolver state. `/museum` receives no
  editor cache, auth, API, or logical-project resolution import.

## 6. Acceptance tests

### Resolution helper

1. no logical texture refs returns no hydration work and makes no asset API call;
2. repeated references to one logical URI list/fetch/verify/register once;
3. a metadata-matching cached entry avoids content GET;
4. a missing or mismatched cache entry fetches, checks response MIME, byte size,
   sniffed MIME, and SHA, then returns one staged entry without mutating cache;
5. missing, duplicate, foreign-project, pending, failed, wrong-kind,
   wrong-storage/source, oversized, or incomplete metadata rejects;
6. unauthorized/not-found/network content failures and MIME/size/SHA mismatches
   reject the whole hydration result;
7. abort/stale checks stop later fetches and yield no staged commit.

### Load orchestration

1. a no-asset project preserves the existing successful Load path;
2. a referenced-asset project primes all verified bytes before
   `replaceProjectDocument`, then adopts the fetched asset list/context;
3. any resolution failure preserves the prior project, layout, selection,
   history, baselines, dirty state, identity, and retained bytes;
4. a document/fingerprint/interaction change during hydration prevents cache
   commit and replacement;
5. a second Load, Save, sign-out, or unmount aborts the first and prevents late
   cache/document/status writes;
6. successful Load remains clean, creates no history, resets selection once,
   and reports the loaded version;
7. the P20.3 ready predicate recognizes loaded metadata immediately and ordinary
   Save performs no asset fetch/upload;
8. source pins keep P20.4 helper/API/cache wiring out of `/museum` and
   `/museum/editor`.

## 8. Boundaries and fallback

- No document/schema migration: logical URI remains the durable authored ref.
- No direct R2/browser credential path and no storage URL in project truth.
- No second renderer, loader cache, asset state store, history path, or Load
  transaction.
- No best-effort degraded rendering for a cloud project that claims a durable
  referenced texture.
- P19 immutable versions and P20 no-delete/no-GC policy remain unchanged.

If pre-hydration cannot reuse the current texture source loader, stop before
adding network behavior to rendering and expose the smallest loader invalidation
needed after cache prime. If atomic cache commit requires broader transaction
machinery, keep staged verification and prune target-only entries on failure;
do not replace the document before every referenced byte is verified.
