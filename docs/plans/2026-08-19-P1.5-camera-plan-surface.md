# P1.5 — Camera Plan surface

**Status:** ready for implementation  
**Parent:** [P1 camera overhaul](./2026-08-18-P1-camera-overhaul.md) §C / §D  
**Depends on:** P1.1 shell shipped; B0 standalone camera placement shipped (`674d597`)  
**Unblocks:** P1.6 framing-authoring convergence; P1.7 Camera UI reconciliation

## Outcome

Replace the P1.1 Camera Plan placeholder with a top-down camera-graph authoring
surface mounted in the existing `Camera → Plan` shell cell. Designers can add,
select, move, connect, shape, and delete camera graph elements over the live
architectural Plan backdrop. The surface edits the same scene document,
selection, graph commands, and history used by Camera 3D.

Camera Plan answers where cameras and paths are. It shows every topology edge,
ordered-node numbers, a distinct free-node treatment, relevant interior path
anchors, selection state, and per-direction timing. Plan gestures change only
world X/Z. Authored node and anchor Y remains byte-for-byte unchanged.

The architectural backdrop stays visible and hit-testable: Add Camera needs a
room-floor hit. It is never selectable or mutable in Camera domain. A wall,
opening, object, or room click cannot write `layoutInteraction.selection` or
detach the active camera selection through the layout-selection reducer.

## Out of scope

- Camera view cones, look targets, heading arrows, authored orientation, FOV,
  view breakpoints, framing envelopes, presets, warnings, or comfort diagnostics
  (P1.6 owns framing UX).
- Connection-duration controls in Camera 3D (P1.6). P1.5 authors timing only in
  Camera Plan.
- Sequence reorder gestures on graph edges. Sidebar/timeline remain sole flow
  order owners; edges remain undirected topology without arrows.
- Scene Plan staging (P2), generic UI refresh (P3), GLB import (P4), and measured
  optimization (P5).
- Cross-workspace dragging, new graph-layout coordinates, a second graph, a
  second route/motion implementation, collision/navmesh work, or schema changes.
- `/museum`, `/museum/editor`, or checked-in Chopin relic changes.

## State, props, and dependencies

Add a Camera Plan session state owned by `EditorApp`, high enough to survive the
Camera Plan ↔ Camera 3D component swap but separate from Scene Plan state:

```ts
type CameraPlanTool = 'select' | 'view';

type CameraPlanState = {
  tool: CameraPlanTool;
  planView: PlanViewportState;
};
```

`Add Camera` and `Connect` are not duplicate local FSM states. Their active
state derives from `store.pendingNavigationCommand`; the existing store command
remains the single owner and can continue if the user switches to Camera 3D.
`Select` or `View` cancels an active pending navigation command before switching
local mode. Escape cancels active drag first, then pending navigation, and
returns to Select.

Suggested component split:

- `app/CameraPlanWorkspace.svelte` — surface composition and toolbar;
- `camera-plan/CameraPlanViewport.svelte` — SVG pointer lifecycle only;
- `camera-plan/camera-plan-state.svelte.ts` — session state constructor/types;
- `layout/plan-camera-projection.ts` — extend shared projection with authoring
  profile, camera nodes, relevant anchors, selection/sequence state, and timing;
- `camera-plan/camera-plan-hit.ts` — pure screen-tolerance camera hit resolver;
- `camera-plan/camera-plan-timing.ts` — pure display model around shared route /
  motion duration APIs if projection would otherwise mix inspector concerns.

Exact filenames may follow local conventions. Keep pure geometry/hit/timing code
outside Svelte components. Add no npm dependency.

## Render and visual contract

Build one render model with two semantic parts:

1. architectural layers 1–5 from live `layoutPreview.geometry`, rendered as
   subdued spatial context; and
2. Camera authoring overlay from live `store.document` resolved against
   `store.rooms`.

Camera-authoring projection must emit:

- every connection once, as an undirected curve with no arrowhead;
- every node at its resolved world X/Z;
- `1…N` order labels from `store.mainFlowNodeIds`;
- a distinct unnumbered free-node ring/badge and “Not in order yet” semantics;
- retained/non-flow connection distinction without hiding topology;
- selected/hovered node, connection, and anchor styles;
- interior anchors only for the selected/relevant connection;
- two directional timing readouts per connection, with authored vs automatic
  fallback distinguishable; and
- add/connect placement feedback and the connect rubber band in transient
  interaction layers.

The Camera profile must omit view cones, look targets, portal/collision markers,
view-keyframe markers, FOV/framing graphics, and envelope handles even if the
Scene Plan tour overlay still supports some of those layers. Assert the profile
at projection/model level rather than relying on CSS invisibility.

Paths must follow the exact shared draft curve. Sample
`createDraftConnectionPositionPath` for display/hit testing using the existing
visual sample-count policy; do not draw only the Bézier control polygon and do
not persist generated endpoints.

## Interaction and history semantics

### Select and backdrop

Hit priority is camera node → visible interior anchor → connection curve → empty
backdrop. Tolerances are screen-space constants converted through
`pixelsPerMeter`, so zoom does not make selection unusable.

- Node click selects its position identity.
- Anchor click selects the exact `{ connectionId, anchorId }`.
- Edge click selects the connection and preserves its active direction when
  already known; otherwise it selects forward.
- Empty Select click calls `activeSelection.deselectActive()`.
- Architectural hits never call `selectLayout*`, never write
  `layoutInteraction.selection`, and never become camera selection.

### Add Camera

Toolbar action calls `beginCameraPlacement`. Next valid room-floor click:

1. resolves room through `findPlanHitRoom` against live compiled queries;
2. converts `[x, z]` to `[x, room.floorElevation, z]`;
3. uses room-local `-Z` transformed through `store.rooms` as deterministic
   initial forward direction; and
4. calls `createPendingNavigationNodeAt`.

B0 commits one standalone free node and selects it in one scene-history entry.
Invalid backdrop clicks keep the command armed and report the existing tagged
room-floor message. Grid snapping may adjust X/Z only; if the snapped point no
longer belongs to the hit room, use the unsnapped valid point.

### Connect

Connect requires a selected source node and calls `beginConnectExistingNodes`.
Pointer movement draws a rubber band from resolved source X/Z to cursor X/Z.
Clicking a destination node routes through `selectNavigationNode`, allowing the
existing pending-command branch to validate and commit the connection. It must
not write flow order except the shipped two-free-node seed rule already owned by
`connectNavigationNodes`. Empty/backdrop clicks leave Connect armed; Escape or
Select/View cancels and restores prior selection.

### Node drag

Selection occurs before drag. Start one document transaction only after pointer
movement crosses the drag threshold. At every move:

1. read the node's resolved world position;
2. replace world X/Z, preserve exact world Y;
3. convert the result back through `store.rooms.localPoint(node.roomId, world)`;
4. call `updateNavigationNodePoint(nodeId, 'position', localPoint)`.

Pointer-up commits one history entry. Escape, pointer cancel, lost capture, or
unmount cancels the transaction and restores the document. Click without drag
creates no history entry. Room ownership does not silently change.

### Path shaping

Existing-anchor drag follows the same threshold/transaction lifecycle, using
`getScenePathAnchorWorldPosition`, replacing world X/Z only, and passing the
result to `updateConnectionAnchorWorldPoint` so existing room ownership and Y
are preserved.

Dragging an edge with no hit anchor starts direct path shaping only after the
threshold: begin one transaction, resolve nearest progress on the exact shared
curve, convert to the smooth draft, insert one interior anchor at the matching
index, then drag it in X/Z while preserving the sampled curve Y. A plain edge
click only selects. Commit/cancel behavior matches Camera 3D direct-path edits,
including `directPathInteractionActive` guard ownership.

### Delete and undo

Delete routes to existing selected-anchor/node/connection commands. Connection
deletion keeps existing validation: required flow edges, detour returns, and
disconnecting deletions reject atomically and never rewrite sequence. Add,
connect, delete, node drag, anchor insert/drag, and timing edit each produce one
scene-history entry. Selection, hover, pan, zoom, toolbar changes, and failed /
cancelled gestures produce none.

## Timing authoring

Camera Plan connection Inspector owns a Forward/Reverse direction switch. For
the active direction it shows:

- path length in metres from the exact shared draft path;
- authored duration field in seconds, or clearly marked automatic fallback;
- effective duration from `resolveCameraMotionDuration` / shared motion setup;
- derived speed `length / effective duration`; zero-length/zero-duration paths
  show `0 m/s`, never `NaN` or infinity; and
- “Use automatic” action that removes only `durationSeconds`, preserving any
  existing easing field. If no timing fields remain, pass `null`.

Writing calls `setConnectionTiming(connectionId, direction, timing)` and keeps
its existing finite-positive validation and transaction boundary. Bending or
moving a path preserves authored duration; reactive projection recomputes
length and speed. Each edge label shows both directions' effective duration,
including formula-derived values when no duration is authored. Use clear
direction labels (`A→B`, `B→A`) while keeping the edge itself arrowless.

## Inspector routing

Change the current blanket “Plan is read-only” gate into workspace-specific
authority:

- Scene Plan keeps the existing read-only behavior for preserved scene/camera
  selections.
- Camera Plan mounts Camera Plan inspector content.
- Camera 3D keeps current `EditorCameraInspector` behavior unchanged; duration
  controls do not leak there before P1.6.

Camera Plan node content may edit name and world X/Z and show sequence /
connection metadata. It must not expose target handle, target XYZ, FOV, aim, or
framing controls. Anchor content exposes world X/Z only. Connection content
exposes endpoints, path metadata, timing, validation, and valid deletion. A
persisted view-keyframe selection remains selected across the view switch but
gets only a passive “Edit framing in Camera 3D” message—no Plan framing UI and
no selection coercion.

## Mount, unmount, and selection continuity

- `CameraPlanWorkspace` mounts only for `domain === 'camera' && view === 'plan'`.
  Scene Plan remains `PlanWorkspace`; Camera 3D remains `Workspace3DView`.
- Camera Plan pan/zoom/grid/snap/local Select/View preference lives at the app
  root and survives Plan ↔ 3D. It never reuses or mutates Scene Plan's local
  authoring mode.
- `store.navigationSelection`, discovery direction, graph identity, Sequence
  panel, timeline playhead/playback/height/expanded state, and history survive
  Plan ↔ 3D unchanged.
- An in-flight pointer transaction cannot survive viewport unmount; cleanup
  cancels it. Store-owned Add/Connect commands may survive and continue in 3D.
- Camera picks clear layout selection only through the existing navigation
  activation hook. Backdrop hits do not activate layout selection.
- Import/reset/undo reconciliation must degrade stale node/connection/anchor
  identities through existing store rules; Camera Plan owns no duplicate
  selection slot.

## Acceptance tests

### Projection and visual rules

1. Camera-authoring profile emits all topology edges once with no arrow token;
   retained edges remain visible; guided order changes numbering, not edge set.
2. Ordered nodes show stable 1-based order; free nodes remain unnumbered and
   visually distinct.
3. Selected node/connection/anchor styles follow the shared navigation
   selection; anchors appear only for the relevant connection.
4. Exact shared curved-path samples, generated endpoints, and interior-anchor
   IDs project correctly; generated endpoints never enter scene JSON.
5. Camera profile emits no cones, targets, heading/framing arrows, view keys,
   FOV, or envelope primitives.
6. Both direction labels show effective duration. Authored duration overrides
   formula fallback; path bending preserves duration and changes derived speed.

### Hit, gesture, and coordinate rules

7. Camera hit priority is node → anchor → edge → empty and remains stable at
   multiple zoom levels.
8. Add Camera accepts room floor, uses compiled floor elevation and room-local
   forward, commits one free node, and rejects wall/outside hits without layout
   selection.
9. Connect shows rubber band and creates one straight connection through the
   existing command; sequence changes only under the shipped two-node seed.
10. Node drag and existing/new anchor drag preserve exact world Y in yawed and
    unrotated rooms, change only X/Z, and retain owner IDs.
11. Click-only, failed, Escape-cancelled, pointer-cancelled, and unmounted drags
    leave document/history unchanged; successful gesture yields one undo step.
12. Empty/background Select click clears camera selection but never writes a
    layout selection. Wall/opening/object/room hits cannot detach camera
    selection except explicit empty-click deselection.

### Inspector, lifecycle, and isolation

13. Forward/reverse timing edits write only chosen direction, preserve easing,
    reject non-positive/non-finite values, undo in one step, and clear back to
    automatic without leaving empty timing objects.
14. Camera Plan node/anchor inspector exposes X/Z but no Y mutation; no target,
    FOV, aim, view-key, or framing controls mount. Camera 3D stays unchanged.
15. Node, connection, anchor, direction, timeline, and Camera Plan viewport
    preference survive repeated Camera Plan ↔ 3D switches. Active drag cancels
    safely on unmount; pending Add/Connect remains store-owned.
16. `EditorApp` mounts no placeholder; Scene Plan has no camera mutators; Camera
    Plan contains no `selectLayout*` mutation path; timeline remains gated by
    Camera domain.
17. `tests/lib/editor/app/contracts.test.ts` relic-isolation and route-wiring
    guards stay green; `/museum` chunks import no editor/app/Camera Plan code.

## Relic, visitor, and architecture boundaries

- One navigation graph and one motion path only:
  `camera-route.ts` + `camera-motion.ts`. Camera Plan projects their output; it
  does not fork them.
- Scene document remains camera topology truth. Layout remains architecture
  truth; `rooms.ts` keeps architecture SoT until its existing gates. No layout
  state drives `/museum` early.
- Scene JSON v6 stores interior connection anchors only. Never persist generated
  node endpoints or Plan-only coordinates.
- Camera Plan helpers remain editor-only and outside visitor imports.
  `/museum/editor` stays on frozen `MuseumEditorApp`; `/museum` stays visitor-only.
- Svelte 5 runes and existing Threlte/editor patterns only. No `scroll-travel`,
  dependency, schema version, build flag, or commit unless requested.

## Rollback / fallback split

If the increment expands, preserve one working vertical slice and split in this
order:

1. **Read-only graph:** replace placeholder with live shared backdrop, exact
   paths, nodes, order/free visuals, selection, and no-framing assertions.
2. **Spatial authoring:** Add, Connect, X/Z node/anchor drag, path insertion,
   cancellation, and one-entry history.
3. **Timing:** Plan-only Inspector, bidirectional effective labels, derived speed,
   and authored/automatic switching.

Do not ship a backdrop that is pointer-inert for Add Camera, enable layout
selection as a shortcut, expose framing in Plan, duplicate graph/motion state,
or weaken Y/history/selection assertions. If exact shared-curve projection
requires a broad render-model rewrite, keep the read-only surface on the current
shared `PlanRenderModel` and split only the camera overlay adapter—never copy
architectural geometry.
