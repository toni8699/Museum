# P1.4 — Framing envelope invariants and policy

**Status:** shipped — 2026-08-19
**Verification:** full suite 1,802 tests green (1 skipped); `svelte-check` 0 errors / 0 warnings; build clean
**Parent:** [P1 camera overhaul](../../plans/2026-08-18-P1-camera-overhaul.md) §B / §D
**Depends on:** P1.2 serialization shipped; P1.3 sampler/guards shipped
**Unblocks:** P1.6 framing authoring UX

## Outcome

The shipped framing-envelope engine gets a dense, adversarial acceptance matrix
that proves its public guarantees across whole transitions rather than at a few
representative samples. Enveloped motion must keep a finite eye-to-target vector
at least as long as the visitor near clip, preserve canonical node endpoints,
avoid antipodal pops and guard-boundary discontinuities, remain deterministic
under arbitrary seeks, and pace FOV through the same single envelope as target
framing.

P1.4 also supplies pure editor policy for the later P1.6 UI to bind:

- the first key creates an auto-managed envelope from a caller-supplied seed;
- later key additions or moves expand its full-authored plateau as needed;
- deleting keys does not unexpectedly contract the envelope;
- a handle gesture explicitly returns manual state, even if it finishes at its
  starting value; and
- key edits never move a manual envelope.

This increment proves and exposes policy; it does not mount authoring controls or
mutate documents from the existing editor flow.

## Pure auto-managed/manual policy

Add `apps/museum/src/lib/editor/editor-camera-framing-envelope.ts` with a small
pure API. Exact names may follow local conventions, but the state and behavior
must remain explicit:

```ts
type CameraFramingEnvelopeManagement = 'auto' | 'manual';

type CameraFramingEnvelopePolicyState = {
  envelope: CameraFramingEnvelope;
  management: CameraFramingEnvelopeManagement;
};

createAutoManagedFramingEnvelope(
  firstKeyProgress: number,
  seed: CameraFramingEnvelope
): CameraFramingEnvelopePolicyState;

updateFramingEnvelopeForKeyProgresses(
  state: CameraFramingEnvelopePolicyState,
  keyProgresses: readonly number[]
): CameraFramingEnvelopePolicyState;

updateFramingEnvelopeHandleValue(
  state: CameraFramingEnvelopePolicyState,
  edited: CameraFramingEnvelope
): CameraFramingEnvelopePolicyState;

markFramingEnvelopeManual(
  state: CameraFramingEnvelopePolicyState
): CameraFramingEnvelopePolicyState;
```

Policy rules:

1. Validate finite interior key progress explicitly in `(0, 1)` and ordered
   envelope bounds through one local predicate; do not depend on codec error
   machinery.
2. First-key creation starts from the caller's valid seed, expands it so the key
   lies on the `w = 1` plateau (`enterEnd ≤ key ≤ exitStart`), pins
   `exitEnd = 1`, and returns `management: 'auto'`. P1.6 owns the seed's tuned
   ramp width.
3. Auto-managed key changes expand only. Enter-side bounds may move only earlier
   (`enterStart` earlier, then `enterEnd` earlier); exit-side bounds may move only
   later (`exitStart` later, then `exitEnd` toward `1`). If a key precedes the
   seed's `enterStart`, both enter bounds move early enough for that key to reach
   the plateau. Ramps and plateau never narrow when keys move inward or are
   deleted.
4. `updateFramingEnvelopeHandleValue` applies a valid changed value to either
   auto or manual state without changing its management discriminator; exact
   value equality is an identity-preserving no-op. `markFramingEnvelopeManual`
   is the explicit intent event and flips auto to manual even when no numeric
   bound changed. P1.6 must dispatch that event from the handle gesture itself,
   not from a value-difference test.
5. Manual state is stable under all key additions, moves, and deletions.
6. Inputs are never mutated; unchanged transitions preserve object identity,
   changed transitions return fresh state/envelope objects.
7. Empty-key cleanup is a caller decision. The reducer neither deletes a
   persisted envelope nor invents a key.

The management discriminator is deliberately editor policy state, not motion or
scene schema. P1.6 must decide how its gesture/session owns that state before UI
binding; P1.4 does not silently claim cross-session persistence.

## Dense motion acceptance contract

Use deterministic fixture matrices and local numeric helpers in
`camera-motion.test.ts`. No random package or new runtime export is needed.
For each fixture, sample a base grid of at least 1,001 evenly spaced **edge-local
distance-progress** values and map them to motion playhead with the existing
`cameraMotionProgressAtEdgeProgress` helper. Add exact envelope bounds, key
progresses, compiled guard sample progresses, and `±epsilon` neighborhoods
around each boundary through the same mapping. Repeat the resulting playhead set
in a fixed coprime permutation to prove random-access stability. A uniform global
playhead grid is insufficient for multi-edge envelope/ramp assertions.

### 1. Non-degeneracy and finiteness

At every matrix sample:

- position, target, and FOV are finite;
- `distance(target, position) ≥ VISITOR_CAMERA_PROJECTION.near - epsilon`;
- the normalized gaze direction is finite; and
- FOV stays inside `MUSEUM_CAMERA_FOV` and the numeric interval from the minimum
  to maximum involved node/key FOV values for that edge.

Cover ordinary blends, exact collinear straddles, epsilon-offset straddles,
near-antipodal directions, path-through-POI, zero-width ramps, and zero/short
distance paths plus short positive durations already supported by the low-level
sampler. Dense sampling is the executable regression net; the construction-level
invariant remains P1.3's standoff projection, not a claim of formal real-number
proof by enumeration.

### 2. Endpoint and branch matrix

Assert exact pose values, not approximate screenshots:

| Direction/track | Envelope | Expected at `p = 0/1` |
|---|---|---|
| forward + keys | present | canonical oriented node eye/target/FOV |
| reverse + own keys | present | canonical reversed node eye/target/FOV |
| reverse + no reverse keys | present/malformed low-level input | existing `travelFacingEnds`; envelope ignored |
| keys | absent | legacy full-authored samples unchanged |
| no keys | present | automatic samples unchanged |

Also pin that target guards never change eye, FOV, envelope weight, route input,
or node endpoint values.

### 3. Smooth continuity and angular pacing

Measure gaze direction with shortest-arc angle. Derive each sample time exactly
as the engine does:

```text
time(p) = cameraInverseEasing(motion.easing, globalDistanceProgress(p))
          × motion.durationSeconds
```

Here `globalDistanceProgress(p)` is the edge-local value placed in its compiled
global edge span, before inverse easing; this is the same mapping used by
`cameraMotionProgressAtEdgeProgress`.

Angular-rate checks use differences between those derived times, never
`progress × durationSeconds`.

- Where the compiled smootherstep angular-rate remap applies, derive the public
  sampler's expected peak from each adjacent pair of compiled guard directions
  and take their maximum:

  ```text
  segmentPeak[i] = direction[i].angleTo(direction[i + 1])
                   / (time(progress[i + 1]) - time(progress[i]))
                   × angularInterpolationPeakRateFactor

  expectedPeak = max(segmentPeak)
  ```

  Peak sampled rate must converge to and not exceed that derived value plus a
  small numeric tolerance. This accounts for
  `sampleCompiledGuardDirection` applying `smootherstep01` inside every compiled
  segment. For the full-active-interval remap, the compiler's underlying sweep
  is still determined by the shortest-arc direct angle between its active
  endpoints rather than the accumulated raw interval angle. Do not substitute
  `maxAngularRateRadiansPerSecond × angularInterpolationPeakRateFactor`: the
  nominal rate participates in the remap decision through accumulated raw
  interval angle, but neither the endpoint direct angle nor the compiled segment
  angles are capacity-bounded by that decision.
- For `guard: null` raw branches, do not assert a radians-per-second ceiling.
  Assert bounded total swing, no adjacent antipodal/180° pop, and convergence as
  the edge-local sample step is halved. Adaptive
  `maxSampleAngularDeltaRadians` refinement is a geometric resolution policy,
  not a time-domain rate clamp.
- Halving the sample step around each guard boundary must converge rather than
  reveal a fixed jump; antipodal interpolation must follow the deterministic
  great-circle side and never cross a zero vector.
- Forward-order, reverse-order, and permuted seeks return bit-identical target
  arrays for the same progress.
- Zero-width envelope ramps are legal intentional steps and are exempt from the
  smooth-ramp rate assertion; they must still be deterministic, finite,
  non-degenerate, and exact on both sides of the bound.

Bypass-only or standoff-only guards use the acceptance rule for their actual
branch; the angular remap peak bound applies only when compiled rate limiting is
active.

### 4. Singularity and double-whip matrix

Singularity cases vary POI offset on both sides of zero, path orientation,
duration below/at/above angular capacity, and envelope-active interval. Assert
bounded angular motion where capacity permits, deterministic great-circle
fallback where it does not, minimum standoff everywhere, and exact raw automatic
framing wherever envelope weight is zero.

Double-whip cases cover all decision sides:

- late + off-axis + insufficient time → bypass compiled;
- late + aligned → no bypass;
- early/off-axis + sufficient time → no bypass;
- thresholds exactly at and just across off-axis, path-excess, and angular-rate
  policy values; and
- bypass onset/end neighborhoods remain continuous and arrive at Node B exactly.

Tests may inspect existing immutable `edgeViews[0].guard` metadata to prove the
chosen branch, but acceptance is ultimately asserted on sampled public poses.

### 5. FOV pacing

FOV remains the scalar half of the same envelope blend:

- dense samples equal the hand-computed
  `autoFov + (authoredFov - autoFov) × w(p)` after existing interval easing;
- target-only standoff/angular/bypass guards leave every FOV sample unchanged;
- rising/falling non-degenerate ramps are finite and continuous at both bounds,
  do not overshoot, and show the expected smootherstep zero-slope boundary
  behavior under shrinking finite differences;
- degenerate ramps retain their documented deterministic step semantics; and
- larger values remain wider/zoomed out, smaller values tighter/zoomed in.

P1.4 does not impose a new comfort limit. P1.6 may diagnose or guardrail short
FOV ramps while preserving deliberate dolly-zoom authoring.

## Acceptance tests

Focused editor-policy tests:

1. valid first-key seeds before/inside/after the proposed plateau produce one
   ordered, exit-pinned auto state;
2. earliest/latest additions and outward moves expand the plateau; inward moves
   and deletions do not contract it;
3. changed handle values update immutably in both auto and manual state without
   changing the discriminator; an explicit gesture-intent event flips to manual
   even after a drag returns to its starting value; marking already-manual state
   preserves identity; later key mutations preserve exact manual bounds;
4. invalid progress/envelope inputs fail without mutation; value-only exact
   no-ops preserve identity and auto state; and
5. forward/reverse callers get identical pure behavior with no direction leak.

Focused motion tests are the five dense matrices above. Keep P1.3's point tests
as readable boundary regressions rather than replacing them with one opaque loop.

## Manual scenarios

1. Scrub the collinear/POI fixture slowly forward, backward, and by random
   timeline jumps: the view never collapses onto the eye or flips 180°.
2. Scrub a hazardous late/off-axis exit: it takes the direct guarded arrival;
   aligned and long-duration controls retain their natural auto-facing path.
3. Compare target and FOV during enter/exit ramps: both follow one envelope;
   target correction never creates a lens jump.
4. Check a legacy authored connection without an envelope and a reverse edge
   without reverse keys: both remain visually and numerically unchanged.

P1.4 adds no mounted UI, so there is no auto/manual interaction scenario until
P1.6 binds the pure policy.

## Lifecycle, selection, and boundaries

- Pure policy values are caller-owned and have no mount/unmount lifecycle,
  subscriptions, Svelte runes, document transactions, or selection effects.
- `CameraMotion` owns compiled immutable guard data; it dies with the motion.
  Sampling remains allocation-free and shares no mutable cross-motion state.
- One nav + one motion: `camera-route.ts` + `camera-motion.ts` only. Do not create
  a second graph, sampler, FOV track, or geometry compiler.
- `/museum` may consume shared motion fixes; no editor helper enters visitor
  chunks. `/museum/editor` and checked-in relic data remain frozen; keep
  `tests/lib/editor/app/contracts.test.ts` green.
- No generated endpoints are persisted. `rooms.ts` remains architecture SoT.
- No npm dependency and no commit unless requested.

## Rollback / fallback split

If the dense matrix exposes a real P1.3 defect, keep P1.4 open and split by
ownership:

1. land the pure editor policy and its tests (file-disjoint);
2. repair one guard class at a time in `camera-motion.ts`, retaining a minimal
   failing fixture plus the dense matrix; then
3. close P1.4 only when non-degeneracy, continuity, singularity, double-whip,
   and FOV-pacing matrices all pass.

Do not weaken tolerances to bless a discontinuity, move correction into a
consumer, or defer a motion defect to P1.6 UI. If auto/manual persistence becomes
a product requirement during review, stop and amend P1.2/P1.4 schema scope
explicitly before implementation rather than inventing hidden store state.
