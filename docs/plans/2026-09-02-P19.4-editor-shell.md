# P19.4 — guest-first app entry + Project Shell scaffold

**Status:** implemented locally; the tracked P19 Google OIDC/live deployment gate remains.
**Depends on:** P19.1–P19.3 authentication + persistence working end-to-end.
**Purpose:** establish the app-level navigation and guest-to-cloud ownership flow before P20 adds durable project assets.
**Tracker ownership:** the P19 row remains authoritative; this annex does not
register a second standalone plan number.

## Outcome

A user can start creating without authentication, work in the existing Spatial editor, and only authenticate when they attempt to use cloud-owned capabilities such as Save or Load.

The product flow becomes:

```text
Entry
  ↓
Project Hub
  ↓
Project Shell
  ↓
Spatial Editor
```

Authentication is a capability gate, not an application gate.

```text
Guest
→ create/edit normally
→ Save
→ Google sign-in
→ return with draft intact
→ first cloud Save
```

P19.4 introduces only the minimum app scaffolding needed to support that flow. It does not implement the final Project Hub or Project Shell product design.

## Product rules

### Guest authoring is first-class

The following require no account:

```text
New Project
Spatial authoring
Scene / Camera
Plan / 3D
undo / redo
preview
plain JSON export
portable package export
```

Cloud-owned capabilities require authentication:

```text
Cloud Save
Cloud Load
Owned-project list
future cloud asset storage
future Publish
```

Do not create anonymous backend users or guest cloud projects.

A guest project is simply the normal in-memory editor project until the user authenticates and explicitly Saves it.

Target route structure:

```text
apps/editor/src/routes/
├─ +page.svelte
│   # lightweight app entry
│
├─ projects/
│   └─ +page.svelte
│       # Project Hub
│
└─ project/
    └─ [projectId]/
        ├─ +layout.svelte

```

Future routes may eventually fit under the same shell:

```text
/project/[projectId]/experience
/project/[projectId]/assets
/project/[projectId]/publish
```

Do not implement those future surfaces in P19.4.

The current `EditorApp` remains the Spatial authoring application. Do not turn `EditorApp` itself into the Project Shell.

Conceptually:

```text
ProjectShell
└─ Spatial
   └─ EditorApp
      ├─ Scene
      │  ├─ Plan
      │  └─ 3D
      └─ Camera
         ├─ Plan

```

Existing Spatial ownership, selection, history, camera, layout, and rendering contracts remain unchanged.

The route entry contract is deliberately small:

```ts
projectId: string;
loadOwnedProject: boolean;
resumePendingSave: boolean;
```

The route supplies identity and one-shot intent. `EditorApp` remains the sole
live owner of project metadata and the P19 Save/Load coordinator. Do not add a
second project store merely to bridge routing.

# P19.4.0 — route and ownership scaffold

Inspect the current SvelteKit route topology and introduce the smallest route hierarchy necessary for:

```text
/
→ /projects
→ /project/:id/spatial
```

### `/`

The root route becomes a lightweight entry surface instead of mounting `EditorApp` directly.

Minimum actions:

```text
Start creating
Continue with Google
```

`Start creating`:

```text
create local project id
→ navigate to /project/:id/spatial
→ seed EditorApp with that same id
```

No backend call and no authentication.

`Continue with Google`:

```text
/auth/login?intent=projects
→ Google OIDC
→ callback
→ Project Hub
```

Keep the entry page intentionally simple. No onboarding wizard, templates marketplace, marketing site, account settings, or final visual system.

### Compatibility routes

Replace the independent `/editor` mount with a compatibility entry that
creates a fresh local project ID and replace-navigates to
`/project/:id/spatial`. It preserves direct authoring entry without a second
`EditorApp` mount.

Do not change `/museum` or `/museum/editor`.

# P19.4.1 — Project Hub skeleton

Add a minimal app-level project launcher.

This is distinct from the Project Shell.

## Guest state

Conceptually:

```text
Projects

[ New Project ]

Your work is not saved to the cloud.

[ Continue with Google ]
```

A guest can create a new project and enter Spatial immediately.

Do not provide a fake cloud project list.

## Authenticated state

Conceptually:

```text
Projects

[ New Project ]

My Projects
- Project A
- Project B
```

Reuse P19's existing authenticated project-list API.

Selecting an owned project navigates to
`/project/:id/spatial?load=1`. That click is the explicit Load intent. The
Spatial route passes the ID plus `loadOwnedProject=true` to `EditorApp`, which
waits for authenticated session bootstrap and then invokes the existing
guarded P19 Load coordinator. Remove the one-shot query with `replaceState`
after it is accepted; refreshing an already loaded project must not initiate a

load intent. Route identity alone must never trigger a cloud Load: the same
route also represents a new local project.

Keep current P19 semantics:

* blank project does not automatically become the newest cloud project;
* Load remains explicit;
* dirty confirmation remains intact;
* no automatic background project switching.

Do not implement:

```text

sorting UI
trash
favorites

shared projects
templates

```

unless an existing implementation makes one of these effectively free.

# P19.4.3 — guest Save → authenticate → Save

This is the core behavioral addition.

When an unauthenticated guest selects **Save**, do not return a generic `401`.

Present a lightweight auth gate:

```text
Save your project

Sign in with Google to save this project
and access it later.

[ Continue with Google ]
[ Not now ]
```

Do not require authentication merely because the user opened the editor.

## OAuth draft handoff

Google OIDC requires full-page navigation, so preserve the current semantic project before redirect.

Immediately before leaving the editor:

1. Refuse Save under the same P19 guards:

   * active document gesture/transaction;
   * invalid Scene/Layout;
   * unresolved binary/package refs reported by `projectExportBlocker`.

2. Compose the same full project snapshot used by P19 Save.

3. Validate with `@portfolio/project-model`.

4. Store the validated canonical `ProjectDocument` plus bounded handoff
   metadata in one browser-session slot:

Conceptually:

```ts
sessionStorage.setItem('museum:pending-cloud-save:v1', JSON.stringify({
  createdAt: Date.now(),
  project: JSON.parse(validation.canonicalJson)
}));
```

The slot expires after 15 minutes. Its project ID is the only return target;
do not store or accept an arbitrary redirect URL.

This buffer is:

* browser-session only;
* semantic document only;
* created only during an explicit auth-for-Save action;
* not a second project persistence mechanism;
* not an autosave system;
* not an ongoing source of truth after the draft is restored;
* never used for auth tokens.

## Return flow

After Google callback:

```text
callback
→ redirect to editor root with bounded auth intent/status
→ root trampoline accepts only auth=success + intent=save
→ detect a valid, unexpired handoff
→ replace-navigate to /project/:snapshotId/spatial?resume-save=1
→ parse + validate again and require snapshotId === route projectId
→ install the snapshot through the existing atomic full-project preflight/commit seam
→ session bootstrap succeeds
→ submit the captured snapshot through the shared P19 Save coordinator
→ clear handoff
```

Do not invent a separate persistence endpoint for this flow.

The resumed editor must not recapture its blank boot document. Refactor the
current Save only as far as needed into:

```text
captureValidatedSaveSnapshot(live state)
submitSaveSnapshot(captured snapshot)
```

Ordinary Save calls both. OAuth resume constructs the same snapshot shape from
the revalidated handoff, installs it as the current unsaved document, then
calls the same `submitSaveSnapshot`. Save completion continues to set
scene/layout/name baselines from that captured snapshot, so edits made while
the request is in flight remain dirty.

## Failure behavior

If:

* login is cancelled;
* callback fails;
* session bootstrap fails;
* pending snapshot fails validation;
* cloud Save fails;

the handoff must not silently overwrite the currently open project. Consume it
only on a fresh Spatial mount carrying `resume-save=1`, with a matching route
ID and no active gesture/transaction.

Clear the slot only when:

```text
Save succeeds
or snapshot is invalid / expired / route-mismatched
or the user explicitly chooses Discard
```

On authentication or Save failure, keep the restored draft dirty and expose
Retry Save + Discard. Never auto-submit the handoff during an unrelated later
login. Expiration is the abandonment cleanup.

# Guest/local project identity

A new guest project receives a normal project ID immediately:

```ts
project:${crypto.randomUUID()}
```

That same ID becomes the cloud project ID on first successful authenticated Save.

Do not create:

```text
guestProjectId → cloudProjectId migration
```

unless current P19 implementation forces it.

The goal is:

```text
local project
→ authenticate
→ same project becomes cloud-owned
```

with no semantic document identity rewrite.

# Authentication behavior

Reuse P19 Google OIDC identity, PKCE, secure-session, and authorization
semantics unchanged. P19.4 adds one validated login-intent enum (`projects |
save`) to the server-side OIDC login state; it never accepts a return URL.
Callback navigation is bounded:

* `intent=projects` success redirects to `/projects`;
* `intent=save` success redirects to `/?auth=success&intent=save`, whose
  session-storage trampoline resumes the matching pending Spatial draft;
* `access_denied` redirects to `/?auth=cancelled&intent=<validated-intent>`;
* other callback failures redirect to
  `/?auth=failed&intent=<validated-intent>` when `EDITOR_ORIGIN` is configured,
  otherwise retain the bounded API error response.

The root surface shows Retry sign-in / Discard draft for these statuses. No
return URL from the browser is accepted by the API. A pending slot is never
auto-submitted after a callback whose validated intent is not `save`.

P19.4 does not introduce new identity semantics.

Keep:

```text
Google OIDC
→ Museum Editor secure session
→ Fastify/Postgres ownership
```

No:

```text
email login
passwords
guest accounts
anonymous DB identities
browser OAuth tokens
new auth SDK
```

The root entry, Project Hub, and Project Shell may consume P19's existing session presentation state.

They must not implement their own auth state machines independently.

# P19 persistence integration

P19's Save/Load semantics remain authoritative.

P19.4 must reuse:

* canonical full-project composition;
* `validateProject`;
* Save snapshot baseline behavior;
* one-request Save/Load mutex;
* project-name dirty baseline;
* atomic Load preflight/install;
* room-registry handoff;
* selection/history teardown after Load;
* generic ownership `404`;
* unresolved-binary Save blocker.

The existing coordinator gains only the three route/resume inputs named
above and the shared captured-snapshot submission function. Project Hub may
reuse `createProjectAuth` and `createProjectApi` for its one session check and
list request; it must not add another identity or token state machine.

Do not create a second Save implementation for guest-auth handoff.

Think of P19.4 as:

```text
new entry/navigation layer
+
one auth-before-Save continuation
```

over the existing P19 persistence coordinator.

# Acceptance

## Entry

1. Visiting `/` does not instantiate `EditorApp`.
2. Guest can choose Start creating without an API/auth request.
3. Authenticated user can enter Project Hub through the same app entry.
4. `/editor` compatibility behavior is preserved or explicitly redirected according to the plan.
5. `/museum` and `/museum/editor` behavior is unchanged.

## Guest authoring

6. Guest can create a project and use existing Spatial Scene/Camera × Plan/3D authoring normally.
7. Guest authoring does not create a database user or project.
8. Existing undo/redo, selection, camera preview, layout compilation, package export, and JSON export remain unchanged.

## Project Hub

9. Guest Project Hub exposes New Project and Sign in, but no fake owned-project list.
10. Authenticated Project Hub lists only current-user projects using P19.
11. Selecting a cloud project invokes P19's existing guarded Load flow.
12. New-local navigation never auto-loads; owned-project navigation consumes
one explicit `load=1` intent and removes it from the URL.

## Project Shell

13. Spatial mounts under the shell without duplicating editor document/session/history ownership.
14. Switching app-level routes does not create duplicate EditorStore/layout/camera authorities.
15. Experience/Assets/Publish implementation does not enter this slice.

## Save auth gate

16. Guest Save presents the auth gate instead of sending an unauthenticated project request.
17. Continuing with Google captures a validated semantic project handoff before navigation.
18. Invalid/unresolved project state cannot enter the OAuth handoff.
19. No binary bytes or auth tokens enter the handoff buffer.
20. After successful authentication, the snapshot is revalidated and sent through normal P19 Save.
21. First successful Save preserves the existing project ID and establishes cloud ownership.
22. Successful Save clears the handoff buffer.
23. Failed/cancelled authentication or failed Save cannot silently overwrite the current live project.
24. P19 snapshot dirty-baseline race semantics remain intact.
25. Invalid, expired, or route-mismatched handoffs are cleared without
installing or saving; auth/Save failures retain a dirty restored draft with
Retry and Discard actions.

## Regression

26. Full editor test suite passes.
27. API/auth/P19 persistence suite passes.
28. visitor bundle boundary passes.
29. `/museum` performs no auth/API request.
30. `/museum/editor` remains isolated from Project Hub/Shell.
31. no new Scene/Layout/camera/history serialization is introduced.

# Why this precedes P20

P19.4 pins the lifecycle P20 can build on:

```text
Guest project
     ↓ authenticate
Owned cloud project
     ↓
P20 asset registry + R2
```

P20 therefore does not need to invent anonymous asset ownership or guest R2 lifecycle.

Its cloud-asset rule can remain:

```text
local/catalogue authoring available to guest

durable R2-backed project assets
→ require authenticated owned project
```

This keeps P20 focused on asset persistence rather than account/application-shell architecture.
